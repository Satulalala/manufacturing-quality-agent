# 制造质量根因分析 Agent · 初学者学习笔记

> 项目名称：Manufacturing Quality Root Cause Agent（制造质量根因分析 Agent）
> 项目简介：面向新能源汽车制造场景，用户用一句人话提问（如"分析 1 月 1 日到 15 日 A 产线的不良率"），
> 系统自动完成「解析问题 → 查数据 → 算不良率 → 排名可疑因素 → 查知识库 → 输出带证据的报告」，
> 全程可复现、可测试、可追溯。

---

## 一、项目简介、适合人群、前置基础

### 这个项目到底做了什么

制造厂每天产生成千上万条质检记录（哪个工位、哪个班次、哪个供应商、合格还是不合格）。
人工分析慢且容易漏。这个项目做了一个 **Agent（智能助手程序）**：

- 用户输入一句自然语言问题（不用学命令，说人话就行）
- 程序自动：解析条件 → 查数据 → 统计分析 → 从知识库找相关维修案例 → 输出一份"带数据证据"的报告
- 报告告诉你：**最可疑的 3 个因素是谁**（如 W-07 工位），每个都带不良率、样本量、证据和排查建议

最关键的一点：程序**不会编造**——查不到就说查不到，结论只基于真实数据，并且每次都记录"调用了哪些工具"（调用链）。

### 适合人群

- Python 学了基础（函数、类、列表字典）想做个**完整项目**的初学者
- 想学「数据分析 + AI 应用开发」的转型者
- 有制造业/质量背景，想做数字化、智能化的人
- 需要简历项目、准备面试的求职者

### 前置需要掌握的基础

| 基础 | 需要到什么程度 |
|---|---|
| Python | 能写函数、会用列表/字典、懂 try/except 和类型注解 |
| pip 安装包 | 会 `pip install xxx` |
| 统计学 | 均值、标准差、百分比（初中数学水平即可） |
| SQL | 只要懂 `SELECT ... FROM ... WHERE` 就够了（项目里现学现用） |
| 网页 | 使用工作台不要求前端基础；修改界面时会接触 React 和 TypeScript |

**不需要**：深度学习原理、大模型原理、算法——全程"用工具"而不是"造轮子"。

## 二、核心基础概念表格

| 名词 | 通俗解释 | 初学者踩坑点 |
|---|---|---|
| **Agent（代理/智能体）** | 能自动"干活"的程序：收到任务 → 自己决定调哪些工具 → 给出结果。和聊天机器人不同，它是**做事**的 | 别以为 Agent 必须有大模型，本项目先做"确定性 Agent"（规则+工具），再可选接大模型 |
| **LLM（大语言模型）** | 能理解人话的 AI，如 ChatGPT。本项目的 qwen2.5 是本地跑的开源版 | 大模型**会编造**（幻觉），所以答案必须用工具+数据兜底，不能让它直接算数 |
| **LangGraph** | 把工作步骤画成"流程图"再执行的框架：解析→查询→分析→报告，每一步是一个节点 | 别一上来就学，先想清楚流程，再用它实现 |
| **RAG（检索增强生成）** | "先查资料再回答"——像开卷考试，先把相关资料查出来，再给模型看 | RAG 的"检索"这一步才是难点，别只盯着"生成" |
| **Embedding / 向量** | 把文字变成一串数字，**意思相近的文字数字也相近**（"螺丝拧不紧"≈"扭矩偏低"） | 中文要用中文优化的模型（bge-m3），英文模型（nomic）对中文效果差 |
| **候选因素** | 统计上"可疑"的因素。**可疑 ≠ 已证明**（相关性 ≠ 因果性），所以叫"候选"，要人工确认 | 这是制造业的底线，报告必须带这个免责说明 |
| **不良率** | 缺陷数 ÷ 检验总数 × 100% | 别忘了同时展示**样本量**，20 条里 2 条 NG 和 2000 条里 200 条 NG 完全不同 |
| **DuckDB** | 一个能直接查 CSV 文件的轻量数据库，SQL 查数据不用搬进 MySQL | 建视图时**不支持参数绑定**，拼接路径要转义单引号 |
| **React + FastAPI** | React 负责浏览器界面，FastAPI 负责本地 Python 服务 | 界面与 Agent 通过明确的 HTTP API 通信，不能直接互相导入代码 |
| **结构化输出** | 让大模型按固定格式"交作业"（JSON），程序才好读取 | 必须做**校验**，模型偶尔会交不规范作业 |
| **回退（fallback）** | 主方案失败（如网络断了）自动用备用方案 | 回退是"降级"不是"报错"，评测基线要靠它保住 |
| **白名单** | 只允许名单里的表/列/操作，其余一律拒绝 | 白名单要挡住**写操作和读任意文件**，不只是挡"明显恶意"的 |
| **测试驱动开发（TDD）** | 先写"考题"（测试），再写代码让考题通过 | 这是本项目的开发纪律：每个函数都有测试，改代码不怕改坏 |
| **评测集** | 固定的考题集（22 题）+ 标准答案，衡量系统好坏 | 每次改动都跑同一套评测，指标掉了说明改坏了 |
| **调用链（trace）** | 每次运行记录"依次调用了哪些工具" | 这是"可追溯"的关键，日志里必须留 |

## 三、项目完整业务流程（大白话分步讲解）

以用户提问 **"请分析 2026-01-01 到 2026-01-31 A产线的不良率异常"** 为例：

```
① 你输入问题
② 解析问题：抽出「2026-01-01 ~ 2026-01-31」「产线 A」
   （可以用规则，也可以让本地大模型提取；模型抽不中就回退规则）
③ 筛选数据：只保留 1 月份 A 产线的记录（约 1233 条）
④ 算总账：1233 条里 107 条不合格 → 总不良率 8.68%
⑤ 分组对比：分别按 工位/班次/供应商/批次 分组算不良率
   发现 W-07 工位 23.65%（148 条里 35 条 NG）→ 远高于整体
⑥ 按「差异大小 × 样本量」给候选因素打分排序，取前 3
⑦ 趋势检测：看不良率哪天开始变差（前后 7 天窗口对比）
⑧ 异常检测：用 Isolation Forest 找出温度/压力/扭矩的离群记录
⑨ 查知识库：把问题拿去检索维修案例文档，命中《W-07 扭矩偏低批量不良》
⑩ 出报告：结论 + 每个因素的证据 + 知识库引用 + 调用链 + 风险提示
⑪ 标注"需人工确认"：工程师看完现场，点"标记为已确认"
⑫ 全程写结构化日志：问题、筛选条件、每步耗时、结果，存成 JSON
```

关键原则（面试常考）：

1. **统计 ≠ 因果**：W-07 不良率高只是"可疑"，不证明它就是原因，所以叫"候选因素"
2. **能查到的才说**：知识库检索不到就明说"没找到"，绝不编造
3. **全程可追溯**：调用了什么工具、用了什么数据、花了多久，全有记录
4. **安全第一**：查数据的 SQL 只读、白名单限制，恶意语句（DROP/删除）直接拒绝

## 六、分阶段学习路线

### 阶段二：质量分析函数（第 3-4 周）

- **目标**：理解质量指标的计算原理，能独立实现并测试
- **学什么**：
  - 不良率、分组聚合（`defaultdict` 按维度分组再统计）
  - 排序的 `key=` 参数（多条件排序：差异、样本量、名称）
  - Pareto：占比、累计占比；Cpk 公式：`Cp=(USL-LSL)/6σ`、`Cpk=min(Cpu,Cpl)`
  - 标准差：样本标准差（ddof=1）vs 总体标准差——**差 1 的除法，初学者必踩**
  - SPC：均值 ± 3σ 控制线、超限判定
- **在项目里做什么**：实现 `compare_groups` → `rank_candidate_causes` → `analytics/pareto.py` → `analytics/process_capability.py` → `analytics/spc_analysis.py`（顺序就是依赖顺序）
- **练习**：
  1. 手算一组 10 个数的 Cpk，对照程序输出（一个数一个数算，别偷懒）
  2. 构造"前 30 天 2% + 后 30 天 8%"的 60 天数据，验证趋势检测跳变点在第 31 天
  3. 给每个新函数**先写测试**（TDD：先写会失败的测试，再写代码让它过）
- **完成标准**：能不用代码解释"为什么小样本的候选因素要按样本量加权"；能说出 Cp=2.0 和 Cpk=1.5 的区别（中心偏移）

## 八、初学者高频问题 & 避坑清单

### 概念类

**Q1：为什么结论叫"候选因素"而不是"原因"？**
统计上相关不代表因果。W-07 不良率高，可能是设备、工装、物料、人员任何原因。
所以只排序"最可疑"，必须人工去现场确认。这是制造业的职业道德底线。

**Q2：为什么不让大模型直接算不良率？**
大模型算数不可靠（可能算错），而且算完说不清依据。封装成确定性函数：
数字可复现、可测试、可审计——面试官问"为什么封装工具"就答这个。

**Q3：RAG 里"检索"和"生成"什么关系？**
检索负责"找到该看哪份资料"（开卷考试翻书），生成负责"照着资料组织回答"。
模型记不住你公司的知识库，必须先把相关资料查出来再喂给它。

**Q4：mock、ollama、glm 是什么关系？**
同一个解析功能的三种"后端"：mock 是假 LLM（规则模拟，测试用）、ollama 是本地真模型、
glm 是云端真模型。用环境变量切换，程序代码不用改——这叫"可插拔设计"。

### 实操避坑类

| 坑 | 现象 | 解决 |
|---|---|---|
| **中文 embedding 用了英文模型** | 检索结果驴唇不对马嘴（"螺丝拧不紧"查不到扭矩案例） | 换 bge-m3（中文优化），用前先小规模验证几个词 |
| **删了 Ollama 的 `.ollama` 目录** | 拉模型卡在 "pulling manifest" 报找不到 id_ed25519 | 那目录里有身份密钥！重建目录 + 重启 ollama serve 让它重新生成 |
| **改代码后页面没变化** | 浏览器仍加载旧版界面 | 开发时确认 Vite 服务运行；正式启动前重新构建前端，再重启本地服务 |
| **设置环境变量后不生效** | gh/ollama 还是直连失败 | 环境变量在**新开的窗口**才生效，旧窗口不读 |
| **国内下载模型太慢** | 4.7GB 拉一晚上 | 走代理，或从魔搭 ModelScope 下载 GGUF 再 `ollama create` 导入 |
| **向量检索后测试变慢** | 全量测试要 6 分钟 | 正常，本地模型推理是真实成本；可以只跑相关测试模块 |
| **DuckDB 建视图报错** | `Unexpected prepared parameter` | DuckDB 建视图不支持参数绑定，自己转义路径拼接 |
| **token 出现在对话/日志里** | 账号被他人操作风险 | 立即去 GitHub 设置删除该 token，用时再生成 |
| **测试全绿但页面报错** | 部分用例需要本地 Ollama | README 已注明：向量用例连不上时自动回退关键词路径 |

### 学习心态类

- **先跑通再升级**：先用 mock（规则）跑通全流程，再换真实大模型——不要一开始就追新技术
- **每个函数先写测试**：改代码不怕改坏，评测指标掉了一查就知道
- **把"诚实"当功能**：查不到就说查不到、不编造，这是 AI 应用最值钱的行为
- **多问"为什么封装"**：面试官最爱问架构决策，本项目的每个工具层都是答案素材
